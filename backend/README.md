# Backend

FastAPI сервис диспетчеризации: хранит справочные данные, дни и наряды в
PostgreSQL, строит планы с solver-ом и обрабатывает события диспетчера.

## Запуск

Из корня репозитория запустите API вместе с PostgreSQL:

```powershell
docker compose up --build postgres api
```

Адреса:

- API: <http://localhost:8080/api/v1>
- Swagger UI: <http://localhost:8080/docs>
- OpenAPI JSON: <http://localhost:8080/openapi.json>
- Проверка готовности API и подключения к БД: <http://localhost:8080/api/v1/health>

Параметры БД задаются через `DATABASE_URL`. Compose формирует это значение из
`POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB`; при отсутствии переменных
используются значения из `docker-compose.yml`.

## Данные

При `SEED_DEMO_DATA=true` (значение Compose по умолчанию) при старте API
загружается матрица перемещений и, если справочники ещё пусты, начальные
справочные данные и демонстрационный день из `backend/data/`.

Для создания демо-дня на другой дате используйте
`POST /api/v1/demo/days/{date}`. Он создаёт синтетический набор из 30 нарядов,
сдвинутый от демо-шаблона, для дат с `1900-01-01` по `2100-12-31`. Этот набор
предназначен для демонстрации и не заменяет оценочные данные организаторов.
Эндпоинт демо-генерации отключён, если `SEED_DEMO_DATA` не равно `true`.

Если демо-инициализация отключена, загрузите справочные данные через
`PUT /api/v1/reference`, матрицу через `PUT /api/v1/reference/travel-matrix`,
а данные дня — через `PUT /api/v1/days/{date}`. После этого постройте план
вызовом `POST /api/v1/days/{date}/plan`.

## Сценарий оценки по ТЗ

Оркестратор выполняет действия для каждого оцениваемого дня в таком порядке:

1. `GET /api/v1/health` — дождаться готовности сервиса и БД.
2. `PUT /api/v1/reference` и `PUT /api/v1/reference/travel-matrix`.
3. `PUT /api/v1/days/{date}` с `now` и нарядами, известными на этот момент.
4. `POST /api/v1/days/{date}/plan`.
5. Отправлять события через `POST /api/v1/days/{date}/events` по неубывающему
   `timestamp`, после каждого получать актуальный план.
6. Получить итог через `GET /api/v1/days/{date}/plan`.

Модельное время берётся из `now` дня и последнего принятого `timestamp`, а не
из системных часов. Дата-время передаётся в ISO 8601 со смещением; время смен и
режима работы СЦ задаётся местным `HH:MM`. Лимиты контракта: health — до 120 с
после запуска, справочники и матрица — до 60 с, загрузка дня — до 30 с,
построение плана — до 300 с, каждое событие — до 10 с, получение итогового
плана — до 30 с.

Валидатор проверяет каждую версию плана по ограничениям:

| Код | Требование |
|---|---|
| H1 | Профиль, технология и допуск сотрудника (высота) подходят к работе |
| H2 | `DEPOT_START`, `DEPOT_END` и остановки находятся внутри смены |
| H3 | При наличии визитов ровно один перерыв нужной длительности, в окне смены и без пересечений |
| H4 | `slot.start ≤ VISIT.start ≤ latest_start` |
| H5 | Длительность визита соответствует нормативу; учитываются события задержки/передачи |
| H6 | Прибытие учитывает матрицу перемещений; `start ≥ arrival`, `end ≥ start` |
| H7 | Остаток оборудования от `equipment_start` не отрицателен; `RESTOCK` доводит его до `equipment_capacity` |
| H8 | Начало/конец маршрута — в СЦ сотрудника; `RESTOCK` проходит в открытом СЦ и длится не меньше норматива |
| H9 | Каждый наряд ровно в одном разделе: визит, нераспределённые, ПГП или отменённые |
| H10 | У начатой остановки сохраняются сотрудник, наряд, место, `arrival` и `start`; `end` меняется только по допустимым событиям |

Для ПГП учитываются помеченные как `pgp_relevant` наряды одного узла доступа:
эталонная группа содержит не менее трёх нарядов, зарегистрированных в пределах
60 минут. События контракта: `NEW_ORDER`, `ORDER_CANCELLED`, `VISIT_DELAYED`,
`ORDER_TRANSFERRED`, `STAFF_UNAVAILABLE` и `TIME_TICK`. Сценарные файлы содержат
`events` и `triggers`; оркестратор преобразует сработавшие триггеры в обычные
события API — отдельный endpoint для загрузки сценария не предусмотрен.

Оценка выполненного наряда учитывает начало в заданном окне, завершение не
позже `deadline` и соблюдение H1–H10; повторный наряд имеет вес 2. Валидатор
пересчитывает время в пути и итоговые метрики по входной матрице. ПГП
сопоставляется с эталоном по составу группы и времени обнаружения. Для
`LATE_RISK` важна своевременность: предупреждение по затронутому после события
наряду должно быть создано не позднее чем за 30 минут до `slot.start`.

## Целевая функция и дополнительные возможности

Планировщик сначала минимизирует суммарный пробег при соблюдении временных окон,
смен, перерывов, норматива работ и запаса оборудования. После выбора порядка
остановок расписание пересчитывается с учётом времени отправления и часового
коэффициента дорожной загруженности. Для выбора маршрута PyVRP использует
среднее значение заданных коэффициентов; окончательное время каждой поездки и
перепланирование по событиям используют коэффициент именно часа отправления.
Это приближение для статического VRP-солвера, а не гарантия глобального
оптимума для time-dependent VRP.

Поддерживаются следующие дополнительные сценарии:

- `hourly_factors` матрицы применяется по местному часу UTC+5 как при
  построении расписания, так и при пересчёте маршрута после события;
- завершённые фактические длительности сохраняются в `order_facts`; при наличии
  минимум трёх наблюдений медиана по типу работ и технологии используется при
  выборе маршрута, при нехватке — медиана типа работ, затем норматив. В итоговом
  плане длительность визита остаётся `work_type.duration_min` для соблюдения H5;
- наряд `INST_PRIVATE_VLS` в частном секторе планируется на двух доступных
  сотрудниках с общей квалификацией, СЦ, пересечением смен и окна перерыва.
  В маршруте сохраняется `team_staff_ids`; при невозможности собрать бригаду
  наряд остаётся нераспределённым;
- у запланированного визита поле `explanation` содержит причины: квалификация,
  технология, время переезда, соблюдение слота, длительность и оборудование;
- `POST /api/v1/days/{date}/scenarios` пересчитывает вариант без записи в план.
  Можно исключить сотрудников (сначала исключаются сотрудники с меньшим стажем)
  и добавить запас в рюкзак; ответ сравнивает показатели с текущим планом;
- отдельное приложение сотрудника получает маршрут и отправляет отметки
  `CALL_CUSTOMER`, `ARRIVED` и `COMPLETED`. Завершение требует отметки прибытия;
  факт длительности сохраняется для последующих прогнозов. Эти мобильные
  endpoint-ы дополняют, но не меняют организаторскую схему событий.

## Основные маршруты

| Метод | Путь | Назначение |
|---|---|---|
| `PUT` | `/api/v1/reference` | Заменить справочники сотрудников, СЦ, узлов и типов работ |
| `PUT` | `/api/v1/reference/travel-matrix` | Загрузить матрицу времени и расстояний |
| `PUT` | `/api/v1/days/{date}` | Загрузить день и его наряды |
| `POST` | `/api/v1/days/{date}/plan` | Построить план на день |
| `GET` | `/api/v1/days/{date}/plan` | Получить последнюю версию плана |
| `GET` | `/api/v1/days/{date}/orders` | Получить наряды с назначениями |
| `POST` | `/api/v1/days/{date}/events` | Обработать диспетчерское событие и перестроить план |
| `POST` | `/api/v1/days/{date}/scenarios` | Рассчитать сценарий без изменения текущего плана |
| `GET` | `/api/v1/mobile/days/{date}/routes/{staff_id}` | Получить маршрут сотрудника для мобильного приложения |
| `POST` | `/api/v1/mobile/days/{date}/routes/{staff_id}/visits/{order_id}/actions` | Записать звонок, прибытие или завершение визита |

Новый наряд передаётся событием `NEW_ORDER`. API сохраняет его и повторно
планирует работу; если подходящего назначения нет, наряд останется
нераспределённым. Когда для дня уже приняты события, обычное построение плана
возвращает конфликт — дальнейшее перепланирование выполняется через события.

Полный контракт и схемы запросов описаны в
[`api_spec.yaml`](./api_spec.yaml); интерактивная версия доступна в Swagger UI.

## Проверка и границы подтверждения

Локальные демо-данные позволяют проверить запуск и отдельные сценарии, но не
подтверждают итоговую оценку на скрытых данных организаторов. Перед оценкой
используйте загруженные оркестратором справочники, матрицу, дни и события.
README и спецификация описывают контракт; они не являются гарантией, что все
ограничения пройдут валидатор для любого входного набора.
