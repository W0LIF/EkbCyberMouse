# EkbCyberMouse
Хакатон Связи 2026 КиберМыши

## Решение кейса

Проект реализует диспетчеризацию выездных бригад: API принимает справочники,
матрицу перемещений и наряды дня, строит маршруты, а затем пересчитывает
невыполненную часть плана по событиям. Оценочный сценарий организаторов:

1. Проверка готовности API.
2. Загрузка справочников и единой матрицы времени в пути.
3. Загрузка дня с модельным временем `now` и нарядами.
4. Построение плана.
5. Последовательная отправка событий по `timestamp` с получением актуального плана.

Валидатор оценивает каждую версию плана по H1–H10: квалификация исполнителей,
смена, перерыв, временные окна, нормативы работ, время в пути, оборудование,
сервисные центры, учёт каждого наряда ровно в одном разделе и неизменность
уже начатых остановок. Полная схема и точные правила приведены в
[`backend/api_spec.yaml`](./backend/api_spec.yaml), а backend-процесс оценки
описан в [`backend/README.md`](./backend/README.md).

## Интерфейс диспетчера

- План дня показывает маршруты и временную шкалу остановок по данным API.
- Дату плана можно менять по одному дню назад/вперёд или выбрать день в
  календаре. Навигация доступна во всех разделах диспетчерской; календарь
  показывает каждый день от 7 дней назад до 7 дней вперёд относительно
  сегодняшней даты.
- В мобильном приложении сотрудника можно так же переходить по дням и выбирать
  конкретный день в том же диапазоне. История отображается, если для дня
  загружены данные или доступна демо-генерация.
- Карта на Leaflet отображает наряды, СЦ и маршруты; API не передаёт дорожную
  геометрию, поэтому линии на карте соединяют остановки напрямую.
- Разделы нарядов, рисков, ПГП, сотрудников и СЦ используют данные backend.
- Планировщик применяет дорожные коэффициенты по часу отправления, прогноз
  длительности по накопленным фактам и формирует объяснение назначения.
- Совместные установки в частном секторе с ВЛС маршрутизируются как бригада из
  двух сотрудников; сценарный анализ пересчитывает план без его публикации.
- Диспетчер может создать новый наряд из шаблона и отправить `NEW_ORDER`;
  солвер назначает его, если находит допустимый маршрут.

## Отдельное приложение сотрудника

Мобильный клиент находится в `mobile-app/` и не заменяет диспетчерский frontend.
Compose показывает его браузерную версию на <http://localhost:8081>. Для открытия
на физическом телефоне создайте в корне `.env` и укажите IP компьютера в вашей
локальной сети:

```dotenv
MOBILE_PACKAGER_HOSTNAME=192.168.1.25
MOBILE_API_BASE_URL=http://192.168.1.25:8080/api/v1
```

Замените `192.168.1.25` на IP компьютера, затем выполните `docker compose up --build`
и откройте QR-код Expo из логов сервиса `mobile` в приложении Expo Go. Телефон и
компьютер должны быть в одной сети; порт `8081` должен быть доступен. Инструкции
также находятся в [`mobile-app/README.md`](./mobile-app/README.md).

## Запуск приложения

Требуется Docker Desktop с Compose. В корне репозитория выполните:

```powershell
docker compose up --build
```

После запуска:

- интерфейс: <http://localhost:3000>
- API: <http://localhost:8080/api/v1>
- OpenAPI/Swagger: <http://localhost:8080/docs>
- проверка готовности: <http://localhost:8080/api/v1/health>

Compose запускает PostgreSQL, API, диспетчерский frontend и мобильное приложение
(веб-версия и Expo Go). Для локального демо API загружает
набор данных из `backend/data/`, если справочники ещё пусты. Чтобы отключить
демо-данные, установите `SEED_DEMO_DATA=false`; оценочный оркестратор может
загрузить свой набор через API. Спецификация API организаторов находится в
`backend/api_spec.yaml`; наличие демо-данных не означает, что результат уже
проверен на закрытом оценочном наборе.

Демо-генератор API принимает даты с `1900-01-01` по `2100-12-31`. В интерфейсах
можно просматривать дни в окне от недели назад до недели вперёд; стрелки
меняют дату на один день, а календарь позволяет выбрать любой день окна.
Для ещё не загруженного дня API в демо-режиме создаёт синтетический набор на
основе демо-шаблона. Эта генерация нужна только интерфейсу и не заменяет
загрузку оценочных данных организаторами через `PUT /api/v1/days/{date}`.

Чтобы просмотреть вчерашний день или любой другой день доступного окна,
используйте стрелки или календарь. Если данных за выбранный день нет, при
включённом `SEED_DEMO_DATA` будет создан демонстрационный день; в режиме оценки
исторические данные должны быть загружены оркестратором.

## Создание наряда

В интерфейсе можно создать наряд вручную через кнопку «Создать наряд».
Форма использует выбранный существующий наряд как шаблон: копирует объект,
тип работ и требуемое оборудование, а диспетчер задаёт время слота. Новому
наряду назначается свободный ID вида `ORD-YYYYMMDD-NNNN`.

При отправке интерфейс вызывает `POST /api/v1/days/{date}/events` с событием
`NEW_ORDER`. API сохраняет наряд и перестраивает текущий план. Солвер пытается
назначить наряд сотруднику с подходящими допусками и доступным временем; если
допустимого назначения нет, наряд появится в списке нераспределённых. Поэтому
создание наряда не гарантирует его назначение.

Нераспределённый наряд можно назначить вручную: откройте его карточку из списка
«Нераспределённые», нажмите «Назначить сотрудника» и выберите сотрудника. API
проверит допуск, технологию, смену, слот и оборудование, построит новую версию
плана и вернёт причину, если выбранный сотрудник не подходит.

Это отличается от генерации демо-дня: `POST /api/v1/demo/days/{date}` создаёт
синтетический набор из 30 нарядов для демонстрации и доступен только при
`SEED_DEMO_DATA=true`. Для оценочного запуска данные должны поступать от
организаторов через API, а не из демо-генератора.

Сервис использует модельное время из `now` загруженного дня и `timestamp`
события, а не системные часы. Важные лимиты организаторского контракта:
построение плана — до 300 секунд, обработка события — до 10 секунд.

Для разработки фронтенда отдельно:

```powershell
cd frontend
pnpm install
pnpm run dev
```

Vite проксирует `/api` на `http://localhost:8080`. Для API используйте Python
3.11+, зависимости из `backend/requirements.txt` и PostgreSQL по настройкам
`DATABASE_URL`.
